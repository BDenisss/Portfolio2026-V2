### F1 — Sécurité — HIGH — `phone` et `contactTo` lisibles anonymement via `/api/globals/site` et GraphQL
- Fichiers : `src/infrastructure/cms/payload/globals/Site.ts:11` (`access: { read: anyone }`), champs `phone` (l.106) et `contactTo` (l.118) sans `access` de champ ; commentaire contredit : `src/composition/contact.ts:21` (« il n'est jamais exposé au public »).
- Preuve : base avec `contact_phone='PROBE-PHONE'`, `contact_contact_to='probe@example.invalid'` (valeurs factices), puis anonyme :
  `curl /api/globals/site` → `{'phone': 'PROBE-PHONE', 'showPhone': False, 'contactTo': 'probe@example.invalid'}` ;
  `POST /api/graphql {"query":"{ Site { contact { phone contactTo } } }"}` → `{"data":{"Site":{"contact":{"phone":"PROBE-PHONE","contactTo":"probe@example.invalid"}}}}`.
  `showPhone: false` ne protège rien : il ne filtre que l'affichage du composant. Aujourd'hui les deux champs sont vides en seed (anonyme : `phone: null`, `contactTo: null`), donc la fuite se produit dès que le propriétaire renseigne l'un des deux dans `/admin`.
- Réfutation tentée : pas voulu (le commentaire de composition dit le contraire), pas listé dans le quality-report, reproduit. Survit.
- Correctif minimal : `access: { read: isAdmin }` sur le champ `contactTo` ; pour `phone`, un `hooks.afterRead` qui vide la valeur quand `showPhone` est faux (ou lecture serveur avec `overrideAccess: true` dans le mapper et lecture publique du champ interdite). Test d'intégration : `GET /api/globals/site` anonyme ne contient ni `phone` ni `contactTo`.
